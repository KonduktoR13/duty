Ты находишься в новой подпапке "pwa" существующего проекта Android-приложения «Мои смены».

Нужно спроектировать и реализовать с нуля полноценную PWA-версию приложения. Существующий Android-проект в родительском каталоге используй как источник требований, примеров PDF, правил парсинга, поведения интерфейса и уже решённых продуктовых задач.

Главная цель

Создать современное installable PWA для просмотра индивидуального рабочего графика из общего месячного PDF.

Приложение должно одинаково хорошо работать на:

- Android;
- iPhone/iPad;
- Windows/macOS/Linux;
- современных Chromium-браузерах;
- Safari/iOS.

Приоритет — mobile-first.

Приложение должно быть offline-first и local-first.

После первоначальной загрузки PWA основные функции должны работать полностью без интернета.

Ключевой принцип приватности

Рабочие графики являются локальными данными пользователя.

PDF, распознанные смены, выбранный Delta-номер, настройки и история импортов:

- не должны загружаться на наш сервер;
- не должны передаваться разработчику;
- не должны уходить в стороннюю аналитику;
- должны обрабатываться непосредственно на устройстве пользователя;
- должны храниться только локально средствами браузера/PWA.

Backend для приложения не предполагается.

В runtime не должно быть сторонней аналитики, рекламы, telemetry и ненужных внешних сетевых запросов.

По возможности все используемые библиотеки и ресурсы должны поставляться вместе с приложением, а не подгружаться с внешних CDN.

Перед первой загрузкой PDF пользователь должен увидеть короткое и понятное объяснение, что файл обрабатывается локально и никуда не отправляется.

Первый запуск

Не проси пользователя заранее вручную вводить Delta-номер.

Предпочтительный flow:

1. Краткий onboarding/privacy screen.
2. Пользователь выбирает месячный PDF-график.
3. PDF локально анализируется.
4. Приложение определяет присутствующие в документе Delta/D-номера.
5. Пользователь выбирает свой номер из реально найденных вариантов.
6. Выбор сохраняется локально.
7. Приложение показывает только относящийся к нему график.
8. После успешного импорта приложение может предложить подключить Google Calendar.

На следующих месяцах ранее выбранный Delta-номер должен использоваться автоматически, если он присутствует в новом графике.

Если структура PDF изменилась, номер исчез, найдено несколько неоднозначных вариантов или parsing вызывает сомнения, приложение не должно молча делать потенциально неправильный вывод. Нужен понятный fallback/подтверждение пользователя.

Импорт графиков

Изучи существующее Android-приложение и существующие тестовые PDF.

Не переносить Android-код механически. Извлеки из него бизнес-логику и реализуй её нормально для web/PWA.

Нужно корректно обрабатывать:

- импорт нового месяца;
- повторный импорт того же PDF;
- обновлённую версию уже импортированного месяца;
- удаление месяца;
- несколько сохранённых месяцев;
- переход через границу года;
- ошибки и неожиданные форматы PDF;
- отсутствие нужного Delta-номера.

Предотвращай появление дубликатов.

Оригинальный PDF при необходимости можно хранить локально, если это разумно с точки зрения UX и возможностей браузера.

Основной UI/UX

Не копируй Android UI буквально.

Разработай современный, простой интерфейс, ориентированный в первую очередь на телефон.

Главное, что пользователь должен видеть быстро:

- ближайшую смену;
- текущий месяц;
- календарь/список собственных смен;
- понятное переключение месяцев;
- статус импортированного графика;
- доступ к загрузке следующего графика;
- настройки.

Подумай самостоятельно, какой вид лучше использовать на маленьком экране: календарь, agenda/list, комбинацию или адаптивное представление.

Избегай перегруженного интерфейса.

PWA должна ощущаться как установленное приложение, а не просто мобильная веб-страница.

Предусмотри корректные safe areas на iPhone, standalone mode, ориентацию экрана, touch targets, accessibility и системную dark/light theme, если это разумно.

Offline-first

Спроектируй полноценный offline mode.

После установки и хотя бы одного открытия без интернета пользователь должен иметь возможность:

- запустить приложение;
- открыть сохранённые месяцы;
- посмотреть смены;
- импортировать локальный PDF;
- удалить или изменить локальные данные;
- пользоваться всеми функциями, кроме тех, которые объективно требуют внешнего сервиса.

Service Worker/cache strategy выбери самостоятельно.

Приложение должно корректно обновляться на новую версию без уничтожения пользовательских локальных данных.

Продумай миграции локальной базы при изменении schema.

Локальное хранение

Используй подходящее долговременное browser storage, вероятнее всего IndexedDB или эквивалент.

Отделяй:

- пользовательские настройки;
- исходные документы;
- распарсенные данные;
- метаданные импортов;
- состояние будущей синхронизации Google Calendar.

Не используй localStorage для больших или структурно сложных данных только ради простоты.

Предусмотри функцию:

"Удалить все локальные данные"

с понятным подтверждением.

Google Calendar

Полноценный Google Cloud Project, OAuth Client ID и production credentials пока отсутствуют.

Сейчас:

- спроектируй архитектуру интеграции;
- подготовь приложение к будущему подключению;
- сделай интерфейс/abstraction так, чтобы реальные credentials можно было добавить позднее без переработки приложения;
- при необходимости используй mock/test implementation;
- документируй, что потом потребуется настроить в Google Cloud.

Предпочтительная будущая модель:

- пользователь явно подключает свой Google Account;
- приложение получает только минимально необходимый доступ;
- создаёт отдельный Google Calendar для смен данного пользователя;
- управляет только календарём, созданным этим приложением;
- не получает ненужного доступа ко всему личному календарю;
- синхронизация инициируется пользователем;
- локальное приложение остаётся полноценным даже без Google Calendar.

После первого успешного импорта уместно ненавязчиво предложить синхронизацию.

Продумай модель синхронизации так, чтобы повторный импорт исправленного графика позволял корректно:

- добавить новые смены;
- изменить изменённые;
- удалить отменённые;
- не создавать дубликаты.

Локально должно быть понятно:

- синхронизирован ли месяц;
- есть ли несинхронизированные изменения;
- когда выполнялась последняя синхронизация.

Не хранить чувствительные OAuth credentials небезопасным способом.

GitHub Pages

В будущем PWA будет размещаться на GitHub Pages.

GitHub-репозитория и remote пока может не быть — пользователь создаст их позже.

Уже сейчас архитектура и build должны быть совместимы с GitHub Pages, включая размещение приложения не обязательно в "/", а потенциально в repository subpath.

Не помещай в исходный код никакие secrets.

Нужно подготовить нормальный production build и, если это имеет смысл, workflow/config для дальнейшего автоматического deploy через GitHub Pages, но не пытайся самостоятельно создавать внешний GitHub-репозиторий или публиковать приложение.

Security

Исходи из того, что весь frontend-код публичен и доступен для просмотра.

Поэтому:

- никаких secrets во frontend;
- никаких Google client secrets;
- никаких служебных PDF;
- никаких встроенных рабочих графиков;
- никаких hardcoded персональных Delta-номеров;
- никаких сторонних trackers;
- минимизируй supply-chain поверхность;
- фиксируй версии зависимостей;
- не используй внешний runtime-код без необходимости;
- добавь разумную Content Security Policy и другие подходящие browser security меры, если они совместимы с выбранной архитектурой.

Проверь фактические network requests приложения. В обычной офлайн/локальной работе после загрузки приложения не должно происходить скрытой передачи пользовательских данных.

Работа с существующим Android-проектом

Родительский Android-проект считать read-only reference.

Можно:

- исследовать код;
- запускать существующие тесты;
- изучать PDF parsing;
- читать документацию;
- использовать имеющиеся тестовые материалы;
- сравнивать результаты Android и PWA.

Нельзя без веской необходимости изменять Android-проект.

Вся новая реализация должна находиться внутри "pwa".

Выбор технологий

Конкретный frontend stack, build system, state management, PDF library, IndexedDB abstraction, testing framework и структуру проекта выбери самостоятельно после исследования задачи.

Критерии выбора:

- хорошая поддержка PWA;
- iOS Safari compatibility;
- небольшой размер;
- простота сопровождения;
- отсутствие лишней серверной инфраструктуры;
- возможность нормального automated testing;
- безопасность;
- долгосрочная поддерживаемость.

Не усложняй архитектуру без пользы.

Это небольшое приложение для примерно 8 пользователей с потенциальным ростом примерно до 15, а не SaaS на тысячи клиентов.

Тестирование

Это важная часть задачи.

Особенно тщательно тестируй parsing PDF, потому что неправильное определение рабочей смены значительно серьёзнее визуального бага.

Создай автоматические regression tests на имеющихся примерах графиков.

Если возможно, сравнивай полученный результат с существующим Android-приложением.

Покрой тестами как минимум:

- parsing;
- определение доступных Delta-номеров;
- выбор нужного пользователя;
- даты/время смен;
- переходы месяца/года;
- повторный импорт;
- обновлённый график;
- удаление;
- предотвращение дубликатов;
- сохранение/восстановление локальных данных.

Протестируй PWA/offline поведение.

Используй browser automation/end-to-end tests там, где они дают реальную пользу.

Особое внимание:

- Android Chrome;
- iOS Safari/PWA standalone peculiarities;
- desktop Chromium;
- responsive layouts.

Если физически протестировать Safari/iOS из текущей среды нельзя, явно зафиксируй это и подготовь manual test checklist вместо того, чтобы делать вид, что проверка выполнена.

Порядок работы

Не начинай с бессистемного написания UI.

Сначала:

1. исследуй существующий Android-проект;
2. пойми реальные PDF и business logic;
3. проверь ограничения PWA/iOS/offline;
4. спроектируй архитектуру;
5. составь внутренний implementation plan;
6. после этого реализуй;
7. запускай тесты и проверяй результат в процессе;
8. самостоятельно исправляй обнаруженные проблемы.

Не спрашивай меня о мелких технических решениях, которые можешь обоснованно принять сам.

Спрашивай только если обнаружишь продуктовую неоднозначность, которая действительно влияет на поведение приложения и которую нельзя надёжно разрешить из существующего Android-проекта или документов.

Definition of Done

На данном этапе задача считается выполненной, когда существует локально запускаемая production-ready основа PWA, которая:

- устанавливается как PWA;
- корректно работает на мобильных и desktop;
- импортирует реальные рабочие PDF;
- после первого импорта предлагает выбрать найденный Delta-номер;
- отображает персональный график;
- сохраняет всё локально;
- полноценно работает offline;
- имеет безопасную local-first архитектуру;
- не зависит от backend;
- готова к размещению на GitHub Pages;
- архитектурно готова к Google Calendar OAuth/API;
- имеет автоматические тесты критичной логики;
- имеет документацию для последующей настройки GitHub и Google Cloud.

Если при исследовании найдёшь более удачное техническое или UX-решение, чем описанное здесь, можешь его применить, если оно сохраняет основные требования: privacy, local-first, offline-first, cross-platform, mobile-first и надёжность определения смен.
